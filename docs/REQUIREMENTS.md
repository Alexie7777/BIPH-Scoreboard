## 0. 结论摘要

**要解决什么**:把 `scoreboard.best` 换成本地自托管版本,核心诉求是**计时器不再依赖网络**;产品形态沿用其"手机计分 + 大屏显示 + OBS 叠加"三件套;v1 只做篮球,架构上为其他球类留好扩展位。

**三条核心结论**:

1. **计时器不稳定的根因已经定位到具体代码,不是"网络慢",是"数据模型错了"。**
   竞品把剩余时间作为**格式化字符串**(`"07:22"`)随比赛状态一起同步,大屏直接原样渲染,**不做任何本地推算**。因此:网络延迟 → 大屏恒定滞后;网络中断 → 大屏时间**冻结**;网络恢复 → 时间**跳变追帧**。这几件事正是你们看到的现象。

2. **正确解法是「锚点(anchor)模型」而不是「同步时间值」。**
   服务端只保存一个事实:*"在服务器时刻 T,还剩 R 毫秒,且计时是否在跑"*。客户端拿到这个锚点后,用自己的单调时钟本地推算剩余时间。消息自带时间戳 ⇒ **迟到、重复、乱序、丢包都不会算错**;断网期间大屏照常走秒。服务端每 1 秒发一次轻量心跳,重连后 1 秒内自动对齐。

3. **自托管到校园局域网是结构性改善,锚点模型是正确性保障,两者叠加才稳。**
   局域网把公网往返(50~300ms + Cloudflare 中转 + Supabase Postgres 变更事件)变成 LAN 往返(<2ms),消掉了 95% 的抖动来源;但只要网络存在抖动,锚点模型保证**时钟永远不会错**。没有锚点模型,再快的网络也救不了断网那一秒。

**范围外**:公网暴露、多租户、注册账号、赞助商市场、SEO 页面、15 个球类、18 套模板 —— 一律不做。

## 1. 竞品拆解:scoreboard.best 到底怎么跑的

### 1.1 架构还原(实测)

| 维度 | 结论 |
|---|---|
| 前端 | Next.js App Router(RSC + 客户端 bundle) |
| 后端 | Supabase(Postgres 作为比赛状态存储 + Realtime 推送) |
| 边缘 | Cloudflare(CDN / Bot 防护 / Analytics / AdSense) |
| 实时通道 | `postgres_changes` → `UPDATE` → `filter: id=eq.<matchId>` |
| 降级策略 | 显示端在 Realtime 掉线时改用 **3 秒轮询** `GET /api/matches/:id`;控制端 **1 秒轮询** |
| 访问控制 | 无注册;`controlToken` + 三档 operator token:`full` / `score` / `graphics` |
| 状态体 | 单个 `match` 文档:`home`/`away`/`clock`/`shotClock`/`presentation`/`overlay` + 各球类可选子状态 |
| 实测体积 | `GET /api/matches/demo-match` → 5,340 字节(含 24 名球员) |

### 1.2 计时器不稳定的根因链(代码级证据)

**证据 A — 状态模型:时间是字符串,不是数值 + 基准时刻**

```json
"clock": { "periodLabel": "Q", "period": 3, "timeRemaining": "07:22", "running": false }
```

整个 `match` 文档里**没有任何**"计时从何时开始"的基准时间戳。客户端拿着这份数据,**没有任何办法**推算"现在还剩多少秒"——它只能等下一个字符串。

**证据 B — 大屏渲染:原样渲染,不插值、不本地走秒**

```js
// FIBA 模板
children: F.clock.timeRemaining
// 通用模板
children: h ? r.clock.running ? r.clock.timeRemaining : "01:00" : r.clock.running ? r.clock.timeRemaining : ...
```

`F.clock.timeRemaining` 直接进 JSX。**大屏显示的每一个数字,都是服务端最后一次成功送达的字符串。**

**证据 C — 推送与降级:Postgres 变更事件不可回放**

```js
let n = t.channel("match-".concat(v.id))
  .on("postgres_changes", { event:"UPDATE", schema:"public", table:"matches", filter:"id=eq.".concat(v.id) }, ...)
  .subscribe(e => {
    ("CHANNEL_ERROR" === e || "TIMED_OUT" === e) && (l=!1, F("Realtime fallback")),
    ("SUBSCRIBED"      === e)                     && (l=!0, F("Realtime"))
  });
e = window.setInterval(() => { l || o() }, 3e3);   // 只有 Realtime 掉线时才轮询
```

Postgres 变更事件在断线期间**不补发**。断线窗口内错过的更新永久丢失,只能靠 3 秒轮询兜底;而轮询只能恢复**状态**,恢复不了**过程**。

**证据 D — 唯一一处本地推算,只用在"通用计时器"上,而不是比赛时钟**

```js
if ("live" === d.status) {
  let e = new Date(d.updatedAt).getTime(),
      s = setInterval(() => {
        let s = Math.floor((Date.now() - e) / 1e3),          // 从 updatedAt 起算的"已过秒数"
            l = Math.floor(s/60).toString().padStart(2,"0"),
            a = (s%60).toString().padStart(2,"0");
        h(l + ":" + a)                                       // 倒着显示 → 实际是"已过去多久"
      }, 1e3);
}
```

这说明他们**具备**本地走秒的能力,但只用在独立的计时器小工具上;**比赛时钟没有享受到这个待遇**。这就是设计缺口所在。

**根因链**

```
服务端每秒把 timeRemaining 减 1 并写库
      ↓  Postgres 写入
      ↓  Supabase Realtime 变更事件
      ↓  公网往返 + Cloudflare + 可能的限流
      ↓
大屏拿到新字符串并渲染
```

链条上**每一环**都会引入延迟与丢失概率,于是:

| 网络状况 | 大屏观感 |
|---|---|
| 正常 | 恒定滞后 ~一个 RTT(几十到几百 ms) |
| 抖动 / 丢包 | 同一秒显示两次(看起来"卡一下") |
| 断网 3 秒 | 时间**冻结**,然后跳变 3 秒 |
| 断网 60 秒 | 时间**冻结 60 秒**,恢复瞬间跳变 60 秒 |
| 跨公网高延迟 | 严重滞后,计分员按停表后大屏还在跑 |

**为什么会这样设计**:简单。状态自洽、任意客户端拿到就能渲染、不需要时钟同步逻辑。对一个"网络良好的互联网服务"是合理取舍。
**为什么我们不能照搬**:我们要在**网络不可靠的体育馆**里用,而时钟是整场比赛唯一不能出错的东西。

### 1.3 值得直接借鉴的部分

| 借鉴项 | 说明 |
|---|---|
| 三档令牌 `full` / `score` / `graphics` | 免注册 + 权限分级,现场可以直接把"只读图形"链接给直播组 |

### 1.4 明确不照搬的部分

| 不照搬 | 原因 |
|---|---|
| Google Fonts + `fonts.cdnfonts.com` 的 seven-segment 字体 | 局域网**无外网**时数字会掉字体/变默认字体,大屏直接毁掉。必须本地内置 |
| 3 秒轮询兜底 | 我们要的是锚点自愈,不是轮询 |
| 每次全量下发整个 match(5.3 KB) | 多场地时带宽浪费,应做增量 |
| 广告 / SEO 落地页 / 好友链接 / 赞助商套餐 | 自托管内部工具,零价值 |
| 把 UI 文案和业务逻辑混在一个 Next.js bundle 里 | 我们要后端独立、能写单元测试 |
| 多球类可选字段塞进同一个扁平对象 | 我们用 `sportState` 判别联合,避免 15 个 `undefined` 字段 |

## 2. 使用场景与角色

### 2.1 场景

| ID | 场景 | 关键需求 |
|---|---|---|
| **S1** | **场地大屏**:一块投影/LED,计分员用手机控制 | 远距离可读、断网计时不乱、手机扫码即用 |

| **S5** | **观众自助查看**:场边平板/观众区大屏查看其他场地比分 | 只读模式,多比分卡轮播 |

### 2.2 角色与令牌

沿用竞品的三档模型,但语义重新定义:

| 角色 | 令牌 | 能做什么 | 典型持有者 |
|---|---|---|---|
| **管理员 Admin** | 独立管理密钥(全局) | 建比赛、改规则、管理场地、导出数据 | 体育组老师 |
| **操作员 Operator** | `match.<opToken>` | 全部计分操作:比分、时钟、犯规、暂停、撤销 | 计分员 |
| **图形 Graphics** | `match.<gfxToken>` | 只切场景/标题,不能改比分 | 直播导播 |
| **显示 Display** | 无需令牌(公开) | 只读大屏 | 大屏设备 / OBS |

令牌形式:`/c/<matchId>?t=<opToken>`。**二维码直接印在纸上发给计分员**,不需要账号、不需要注册。
安全边界:显示端公开是刻意的(体育场馆的队名/比分不算敏感),但**操作令牌必须足够长**(`crypto.randomBytes(16)` 十六进制),且不落在服务端日志里。

### FR-2 比赛时钟(核心) `P0`

| ID | 需求 |
|---|---|
| FR-2.1 | **锚点模型**:状态为 `{running, remainingMs, anchorServerTs, period, periodLabel}`;**禁止**存储或传输格式化字符串 |
| FR-2.2 | 服务端权威:只有服务端能改变时钟;所有变更通过命令进入 |

| FR-2.4 | 操作:开始 / 暂停 / 继续 / 重置到节长 / ±1s ±5s ±10s ±30s ±60s / 直接设定具体时间 / 切换节次(+1 / -1 / 下一节 / 上一节) |
| FR-2.5 | 节次显示:`Q1..Q4` / `OT1..` / `HT`(中场)/ `FINAL`;节间可插入**节间倒计时**(默认 2 分钟) |

| FR-2.9 | 最后 60 秒进入"加时显示"样式(可选,红色/闪烁) |

| ID | 需求 |
|---|---|
| FR-3.1 | 独立锚点,与比赛钟同步演进但可单独暂停/重置 |
| FR-3.2 | 重置值可选:**24 / 14 / 30 / 12**,按规则集给默认值 |

### FR-14 权限分层:管理员密钥 vs 控制令牌 `P0`

> v0.5:按 Alex 反馈新增 —— "这些比赛我没有管理员密钥,无法控制比赛"是个误解。
> 事实是**控制一场比赛根本不需要管理员密钥**,需要的是**控制令牌**。
> 这个误解如果留在产品里,现场老师会在没有钥匙的情况下以为开不了赛 —— 所以必须写进需求并落到界面。
>
> v0.14:按 Alex 要求,管理员密钥**写死为 `1818`**。理由:这个密钥防的是**误触**,不是黑客 ——
> 校内封闭网络里,现场真正要挡的是"手滑把正在打的比赛删了"。随机密钥意味着每次部署都要有人
> 先去服务器上把密钥捞出来、抄在本子上、贴在机房门上,实际执行率接近零:闸门形同虚设,
> 反而给人"这里有安全"的错觉。真要更严,启动时用 `ADMIN_KEY` 环境变量覆盖即可。

**两把钥匙,两种职责,互不通用**:

| 钥匙 | 管什么 | 作用域 | 谁拿得到 |
|---|---|---|---|
| **控制令牌** operatorToken | 连控制台 WS,下发计分/计时/蜂鸣命令;**改本场参数**(队名/规则/显示设置) | **一场比赛** | 拿到控制台链接或二维码的人(计分员本人) |
| **管理员密钥** adminKey | **重置比赛、删除比赛**(破坏性操作) | **整台服务器** | 默认 `1818`(已知);要更严就由部署方用 `ADMIN_KEY` 覆盖 |

**核心原则**:**控制比赛与改本场参数都不需要管理员密钥**。管理员密钥只管"把比赛删了/清零了"这类不可逆操作。

### NFR-1 计时与同步(硬性,带验收标准)★

> 这一节是整个项目的立身之本,建议直接作为测试用例。

| ID | 需求 | 验收标准 |
|---|---|---|
| **NFR-1.1** | 大屏时钟**不依赖网络**连续走秒 | 拔掉大屏网线 60 秒,大屏时间连续、无跳变、无归零 |

| **NFR-1.3** | 重连自愈 | 恢复网络后 ≤ 1.0 秒内两端对齐,且**不闪屏、不重置比分** |
| **NFR-1.4** | 消息幂等 / 自描述 | 任意一条状态消息单独即可算出当前显示值;重复投递、乱序投递结果一致 |

| **NFR-1.8** | 服务器崩溃后大屏时间仍准确 | 进程被杀后,大屏继续按锚点走秒,直到锚点耗尽 |
| **NFR-1.9** | 无漂移 | 运行 2 小时后,大屏时间与服务端时间误差 ≤ 200 ms(不累积) |
| **NFR-1.10** | 时钟不因系统时间跳变而错 | 客户端/服务端系统时间被 NTP 修正 ±30s 时,计时不受影响 |

| **NFR-1.12** | 心跳自愈 | 服务端 ≥ 1 次/秒 的轻量时钟广播;客户端检测 `seq` 跳号立即全量拉取 |

**明确接受的取舍**:手机断网期间,如果计分员按了"暂停",该命令无法送达大屏,大屏会**继续多跑最多 1 秒**(心跳周期)直到命令补达。这是有界的、可接受的;比分在断网期间则**完全冻结**,恢复后补齐——因为比分错一秒就是错,不能猜。

## 5. 架构建议

### 5.1 拓扑

```
        ┌──────────────┐   WebSocket   ┌─────────────────────────┐
        │ 计分员手机    │ ────────────▶ │   BIPH 场地管理台 Server (单容器)  │
        │ 控制台 PWA    │ ◀──────────── │   ├─ HTTP  /api  静态资源  │
        └──────────────┘   状态 + 心跳  │   ├─ WS    /ws/:matchId   │
                                 │      │   └─ SQLite (WAL) /data  │
        ┌──────────────┐   WebSocket   │                         │
        │ 大屏 (笔记本/  │ ────────────▶ │                         │
        │ 电视/投影)     │ ◀──────────── │                         │
        └──────────────┘               └─────────────────────────┘
        ┌──────────────┐   WebSocket
        │ OBS 浏览器源  │ ────────────▶
        └──────────────┘
```

要点:
- 全部流量**只在局域网内**,不经过任何公网服务
- 服务器是**唯一状态源**;大屏与控制台都是它的客户端
- 大屏与控制台之间**不直接通信**,全部经服务器中转(简化一致性)

### 5.2 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 语言 | **TypeScript** | 球类插件用 TS 写迭代快,类型共享,AI 辅助编码友好 |
| 后端 | Node.js 20+ / **Fastify** / `ws` / `better-sqlite3` | 单进程、零外部依赖;SQLite 同步 API 简单可靠 |
| 前端 | **React 19 + Vite + TypeScript** | 纯客户端实时应用,SPA 最合适;Vite 构建快 |
| 实时 | **WebSocket**(备选 SSE + POST) | 双向、低延迟;企业代理下 SSE 更稳,可作为降级 |
| 存储 | **SQLite**(WAL) | 一场比赛写入 < 1 KB/s,单文件零运维;导出即拷贝 |
| 部署 | 多阶段 Dockerfile → `node:22-alpine` | 单镜像,`docker compose up -d` |

**为什么不选 Next.js**:这是纯客户端实时应用,RSC 每次导航都要服务器往返,而大屏/控制台都是长驻 SPA;Next 的运行时与心智负担都高于收益。
**为什么不选 Go**:Go 单二进制更省资源(镜像 ~20 MB),但球类插件用 TS 迭代更快。若目标是"一台旧笔记本跑很多年"且**只做篮球**,Go 值得考虑。
**为什么不选 Postgres + Redis**:自托管的核心价值是"一条命令搞定",多一个有状态服务就多一份运维负担。

### 5.3 同步协议

**连接**:WebSocket,每场比赛一个频道 `/ws/:matchId?role=&t=`。显示端与控制端都可连。

**消息**

```ts
// 服务端 → 客户端
type ServerMsg =
  | { t: 'state'; seq: number; serverTs: number; match: Match }            // 全量
  | { t: 'patch'; seq: number; serverTs: number; ops: PatchOp[] }          // 增量
  | { t: 'tick';  seq: number; serverTs: number; clock: ClockAnchor; shotClock: ClockAnchor } // 1s 心跳
  | { t: 'ack';   cmdId: string; seq: number; ok: boolean; error?: string }
  | { t: 'event'; kind: 'log' | 'buzzer' | 'whistle' | 'periodEnd'; payload: unknown }
  | { t: 'pong';  t0: number; serverTs: number };

// 客户端 → 服务端
type ClientMsg =
  | { t: 'cmd'; cmdId: string; type: string; payload: unknown }   // 幂等命令
  | { t: 'ping'; t0: number };
```

**时钟锚点**

```ts
interface ClockAnchor {
  running: boolean;
  remainingMs: number;      // 锚点时刻的剩余毫秒(整数)
  anchorServerTs: number;   // 锚点创建时的服务器墙钟(ms)
  period: number;
  periodLabel: string;
}

// 服务端推算
const remaining = (c: ClockAnchor, nowServer: number) =>
  c.running ? Math.max(0, c.remainingMs - (nowServer - c.anchorServerTs)) : c.remainingMs;
```

**客户端时钟对齐(NTP 式)**

```ts
// 1) 收到任意服务端消息时,重置基准
//    serverNowEst(perfNow) = recvWall + offset + (perfNow - recvPerf)
//    —— 用 performance.now() 单调推进,墙钟只在收到消息时重置
// 2) ping/pong 估计 offset:offset = serverTs - (t0 + t1) / 2,取最小 RTT 样本或 EWMA
```

**自愈**
- 客户端检测 `seq` 不连续 → 立即 `GET /api/matches/:id` 拉全量
- WS 重连 → 立即拉全量 + 重置基准
- 心跳 1s/次 → 最坏收敛 1s

**命令可靠性**
- 每条命令带 `cmdId`(uuid),服务端维护 LRU 去重表
- 控制端未收到 ack → 同 `cmdId` 重试,指数退避,≤3 次
- 命令语义是**转换**(transition):`pause` / `adjust` / `addPoints`,不是**电平**(level)

**状态与表现分离**
服务端只发**事实**(比分 56、犯规 3、锚点),不发送"显示什么";所有格式化、模板渲染、动画都在客户端。

### 5.5 自适应屏幕比例设计规范

> 回答 Alex 的问题 1:是,直接按自适应屏幕比例设计。以下是具体规范。

**核心原则:固定设计画布 + 等比缩放(letterbox),不做流式重排。**

理由:记分牌在不同设备上必须**长得一样**。如果用流式布局,同一场比赛在 4:3 投影仪和 21:9 LED 屏上,元素位置会完全不同,现场没人知道"24 秒"跑哪去了。记分牌要的是**一致性**,不是**填充率**。

**实现方式**

```
设计画布固定 1920 × 1080
容器尺寸 → scale = min(containerW / 1920, containerH / 1080)
根元素   → transform: scale(var(--scale)); transform-origin: center;
所有元素 → 用设计画布内的 px 值(整体已被缩放,无需再自适应)
多余部分 → 留黑边(letterbox),背景色可配
```

**两种适配模式**(模板级配置,不是全局开关)

| 模式 | 行为 | 适用 |
|---|---|---|
| `fit`(默认) | 等比缩放 + 黑边 | 绝大多数情况;内容比例永远正确 |
| `stretch` | 非等比拉伸填满 | 老式 4:3 投影仪放 16:9 内容时,学校可能宁愿拉伸也不要黑边 |

**安全区**

- iPad 控制台:`env(safe-area-inset-*)` + 圆角与 home indicator 避让
- 大屏:四边留 3% 呼吸区,避免内容被投影仪边缘裁切
- 边距可配

**分辨率验收矩阵**

| 设备 | 分辨率 | 比例 | 要求 |
|---|---|---|---|
| 教室投影仪 | 1920×1080 | 16:9 | 设计基准 |
| 老投影仪 | 1024×768 | 4:3 | `stretch` 模式不留黑边 |
| LED 大屏 | 2560×1080 | 21:9 | `fit`,左右黑边可接受 |
| 笔记本 | 1366×768 | 16:9 | — |
| iPad 控制台 | 1024×768 / 1180×820 | 4:3 | 控制台**单独一套**自适应(非等比缩放画布) |

**可读性底线**

- 设计画布下比分数字高度 ≥ 200px(缩放到 1080p 时等效 ≥ 200px)
- 目标:**5 米外**可读出比分与剩余时间
- 验收方式:在目标分辨率截图后人工判断,不达标就调设计画布字号,不靠设备缩放
- 投影环境一律**深色背景 + 高对比数字**,避免白底反光

> 关键提醒:控制台与大屏用**两套不同的自适应策略**。大屏用"固定画布等比缩放"保证多设备一致性;控制台是 iPad 触控界面,需要的是**元素随屏幕重新排布**(横屏双栏 / 竖屏单栏),而不是整体缩放。

### 5.6 多球类扩展机制(球类插件)

**三层正交**,这是"以后加球类不返工"的关键:

| 层 | 决定什么 | 举例 |
|---|---|---|
| **ruleset 规则集** | 分节数、节长、进攻钟长度、犯满/bonus、罚球数 | FIBA / 校规 / 3×3 / 半场制 |
| **sport 球类** | 比分语义(总分/局分)、额外状态 | 篮球(总分) / 网球(局-盘-分) / 排球(局分+轮转) |
| **template 模板** | 纯视觉皮肤 | 简洁大比分 / 复古 LED / 现代转播风 / NBA 风 |

**模板与规则完全解耦**:同一个"简洁大比分"模板必须能渲染任意球类的状态。

**插件接口**

```ts
interface SportModule {
  id: string;
  label: string;
  defaultRuleset: string;
  rulesets: Ruleset[];
  createState(ctx: MatchContext): SportState;
  controlSections(ctx: MatchContext): ControlSection[];  // 控制台额外面板
  displayFields(ctx: MatchContext): DisplayField[];      // 大屏额外字段
  derive(ctx: MatchContext): DerivedState;               // 派生量(bonus、是否罚球…)
  eventMessages(ctx: MatchContext): EventMessageMap;     // 日志文案模板
}
```

**新增一个球类 = 新增一个 `sports/xxx.ts` 模块 + 若干模板**,核心代码零改动。v1 只实现 `basketball`,但 `sports/` 目录、注册表、模板渲染管线在 P0 就要立起来,否则后期是重构而不是扩展。

## 7. 风险与已知坑

| # | 坑 | 影响 | 应对 |
|---|---|---|---|
| 1 | **Service Worker 与 Wake Lock 都要求安全上下文** | 局域网 `http://192.168.x.x` 下 PWA 与防锁屏**全部失效** | 启动时生成自签证书(含 LAN IP SAN)默认开 HTTPS;HTTP 作为降级;防锁屏用静音音频循环兜底(iOS 经典技巧) |
| 2 | **校园网 AP 隔离** | 手机访问不到同网段服务器,全场无法开赛 | 自带路由器/手机热点;提供"显示机本地跑服务端"模式;部署文档写清 |
| 3 | **中文队名 + 七段字体** | 队名掉字体/乱码,大屏直接毁掉 | 数字与文字分字体栈;或内置 CJK 子集字体 |
| 4 | **大屏电脑休眠/屏保** | 时钟冻结、比分停更 | `visibilitychange` 立即重取锚点;部署时关闭屏保与合盖休眠 |
| 5 | **NTP 修正系统时间** | 锚点跨机对齐错乱 | 内部一律单调时钟;墙钟只用于对齐;锚点消息带 `serverTs` 自描述 |
| 6 | **多设备同时操作** | 两台手机同时按分,比分错乱 | 服务端串行化 + 乐观锁(`seq`),冲突命令拒绝并提示 |
| 7 | **校赛规则五花八门** | 规则集写死,现场改不动 | 规则集**数据驱动**且每场可覆盖 |
| 8 | **误触** | 比分错、时钟乱 | 破坏性操作长按/二次确认 + 全局撤销 + 事件日志兜底 |
| 9 | **服务器崩溃 = 比赛丢** | 联赛中断 | SQLite 每命令落盘 + 10s 快照 + `restart: unless-stopped` + 启动恢复 |
| 10 | **无外网时字体/CDN 失败** | 大屏字体崩 | 所有资源本地内置,构建后运行时零外网请求 |
| 11 | **OBS 浏览器源透明** | 直播画面带白底 | `overlay=1` 模式强制透明 body;验收用截图比对 |
| 12 | **大屏分辨率多样** | 文字被裁/太小 | 全部相对单位;提供 4:3 安全区;投影仪与 LED 屏各测一次 |
| 13 | **观众席临时加看** | 需要额外显示源 | 显示端公开只读,支持多客户端;URL 短到能念出来 |
| 14 | **"联赛表"需求后补** | 赛程/积分 | 预留赛事(group)概念,P2 再做,避免现在过度设计 |

| 1 | 大屏实际分辨率与比例(4:3 还是 16:9?LED 屏宽度?) | 拿到设备后 | 只影响验收矩阵,模板本身自适应,不影响实现 |
| 2 | 学校服务器规格(CPU/内存)、是否有 Docker 权限、是否有固定校园网 IP | 部署前 | 影响 compose 配置与并发能力预估 |
| 3 | 能否向学校 IT 申请 `scoreboard.xxx.edu` 域名 + 证书 | 部署前 | 有证书则完全无证书告警;申请不到则用自签证书 + 一次性信任引导 |
| 4 | 校赛规则的具体数值(节数/节长/进攻钟/犯满/暂停次数) | 建比赛时 | 规则参数在 UI 里可改,**不阻塞**,但要提前问清 |
| 5 | 校园网是否开启 AP 隔离 | 首次现场联调 | 决定是否需要自带路由器 |

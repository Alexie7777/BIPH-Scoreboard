把 时钟 从「同步的值」
改成「同步的锚点」

目标:替代 scoreboard.best,做一套可 Docker 自托管、局域网内运行的记分牌。v1 只做篮球,架构上为其他球类留好扩展位。

已完成对竞品的实测拆解 —— 它的计时器抖动根因已定位到具体代码,而非泛泛的「网络慢」。

1 容器零外部依赖,无数据库/Redis/对象存储
60 秒拔网线后大屏计时仍连续不跳变
≤ 1.0s网络恢复后自动对齐,比分不丢不重
128 bit操作令牌长度,免注册、扫码即用

它的计时器为什么会抖

竞品把剩余时间当作格式化字符串随状态一起同步,大屏原样渲染、不做任何本地推算。时钟因此完全寄生在网络送达率上。

证据 A · 状态模型:时间是字符串

// GET /api/matches/:id
"clock": {
  "periodLabel": "Q",
  "period": 3,
  "timeRemaining": "07:22",   // ← 字符串
  "running": false
}

整份状态里没有任何「计时从何时开始」的基准时间戳。客户端拿着它,没有任何办法推算「现在还剩多少秒」——只能等下一个字符串。

证据 B · 大屏渲染:原样输出

// FIBA 模板
children: F.clock.timeRemaining

// 通用模板
children: h ? r.clock.running
  ? r.clock.timeRemaining
  : "01:00" : r.clock.running
  ? r.clock.timeRemaining : …

大屏显示的每一个数字,都是服务端最后一次成功送达的字符串。延迟即滞后,丢失即冻结。

证据 C · 推送与降级:Postgres 变更事件不可回放

let n = t.channel("match-"+v.id)
  .on("postgres_changes", { event:"UPDATE", table:"matches" }, …)
  .subscribe(e => {
    ("CHANNEL_ERROR"===e || "TIMED_OUT"===e)
      && (l=false, F("Realtime fallback")),
    ("SUBSCRIBED"===e) && (l=true, F("Realtime"))
  });
e = window.setInterval(() => { l || o() }, 3000); // 仅掉线时才轮询

断线期间错过的更新永久丢失,只能靠 3 秒轮询兜底 —— 而轮询只能恢复状态,恢复不了过程。

根因链

服务端每秒把 timeRemaining 减 1 并写库
Postgres行更新触发变更事件
公网Supabase Realtime + Cloudflare 中转
大屏原样渲染收到的字符串
延迟 → 恒定滞后显示值落后一个 RTT,公网下可达数百毫秒
断网 → 冻结时间停住不动,观众一眼看穿
恢复 → 跳变追帧补上,秒数突然跳一大截

同一场比赛,两种模型

横轴为比赛真实时间,纵轴为大屏显示的剩余秒数。灰色虚线是真值,绿色是我们的设计,红色是竞品当前行为。

真实剩余时间
锚点模型(我们)—— 与真值完全重合
字符串同步(竞品)—— 中断即冻结,恢复即跳变

绿线之所以能盖住虚线:大屏收到锚点后,用本地单调时钟自己走秒,而不是等网络喂下一个数字。断网期间它不知道「比分」变了,但它知道时间该怎么走。

锚点模型:规则是什么

服务端不再保存「还剩 7 分 22 秒」,而是保存一个事实:在服务器时刻 T,还剩 R 毫秒,且计时正在跑。

状态

interface ClockAnchor {
  running: boolean;
  remainingMs: number;      // 锚点时刻的剩余毫秒(整数)
  anchorServerTs: number;   // 锚点创建时的服务器墙钟(ms)
  period: number;
  periodLabel: string;
}

服务端推算

remaining = clock.running
  ? max(0, clock.remainingMs
      - (nowServer - clock.anchorServerTs))
  : clock.remainingMs

服务端自己用 process.hrtime.bigint() 的单调时钟计时,系统时间被 NTP 修正也不影响。

客户端推算

elapsed = serverNowEst - anchor.anchorServerTs
remaining = anchor.running
  ? max(0, anchor.remainingMs - elapsed)
  : anchor.remainingMs

客户端用 performance.now() 单调推进 serverNowEst,墙钟只在收到消息时重置基准。任何一条消息单独都能算出当前显示值,不依赖上一条。

为什么「消息自描述」是整个设计的关键

每条状态消息都带 serverTs 与 seq。这带来四条性质:

迟到不误晚到的消息自带时刻戳,算出的当前值依然正确
重复无害同一条消息重放,结果完全一致
乱序不乱按 serverTs 取最新锚点即可
丢失可愈心跳 1 秒一次,最坏 1 秒内对齐

时钟对齐(NTP 式)

offset = serverTs - (t0 + t1) / 2     // t0 = 发 ping, t1 = 收 pong
rtt    = t1 - t0
// 取最小 RTT 样本的 offset,或做 EWMA 平滑

// 收到消息时重置基准,之后用单调时钟推进
serverNowEst(perfNow) = recvWall + offset + (perfNow - recvPerf)

用 最小 RTT 样本而不是平均值:抖动只会让部分样本变差,不会让最小值变差。

断网时到底会发生什么

把最恶劣的情况摊开看,明确哪些能接受、哪些必须为零。

阶段 1 · 正常

局域网内稳定同步

控制台、大屏、OBS 三端各自持有同一份锚点,本地走秒。两端误差 ≤ 300ms,与网络无关。

阶段 2 · 断网

大屏继续走秒,比分冻结

大屏用本地锚点继续计时,显示值与真实时间一致。比分保持最后已知值并标注离线——因为比分错一秒就是错,不能猜。控制台离线提示 + 命令本地排队重试。

阶段 3 · 恢复

1 秒内自愈,无跳变

重连即拉全量 + 重置基准。错过的心跳由序号跳号检测补拉。不闪屏、不重置比分。若期间计分员按过暂停,命令会在 1 秒内补达并纠正。

场景大屏时钟大屏比分恢复后
手机 Wi-Fi 抖动 2s连续走秒,无跳变不变≤ 1.0s 自动对齐
手机完全断网 60s继续走秒冻结 + 离线标记命令补发,≤ 2.0s
大屏与服务器断网 60s继续走秒冻结 + 离线标记全量对齐,比分补齐 ≤ 2.0s
服务器进程崩溃继续走秒(锚点已在本地)冻结容器自动重启,≤ 3s 恢复比赛
大屏浏览器崩溃 / 刷新——重新加载后 ≤ 1.0s 对齐
系统时间被 NTP 修正 ±30s不受影响不受影响内部用单调时钟

唯一被接受的偏差:手机断网期间若计分员按了「暂停」,该命令无法即时送达,大屏最多多跑 1 秒(心跳周期)后被纠正。有界、可接受;比分则完全冻结,绝不臆造。

系统拓扑

所有流量只在校园局域网内往返,运行时不请求任何外部域名。

技术选型

TypeScript + Fastify + ws + better-sqlite3,前端 React + Vite。多阶段 Dockerfile 打成单镜像,前端产物由后端进程托管,docker compose up -d 一条命令完成。

不选 Next.js:纯客户端实时应用,SSR 是负担。不选 Postgres + Redis:多一个有状态服务就多一份运维。Go 单二进制更省资源,但球类插件用 TS 迭代更快。

局域网优先的三个硬约束

① 字体全部本地内置 —— 竞品依赖 Google Fonts 与 cdnfonts 的七段字体,无外网时大屏数字直接掉字体。

② 默认开 HTTPS —— Service Worker(PWA)与 Wake Lock(防锁屏)都要求安全上下文,http://192.168.x.x 下两者全部失效。启动时生成含局域网 IP SAN 的自签证书,HTTP 作为降级。

③ 预留 AP 隔离规避 —— 校园网常见客户端隔离,提供自带路由指引与「显示机本地跑服务端」模式。

核心引擎

锚点时钟 · WebSocket 同步 · 事件日志 · 撤销 · 令牌 · 持久化 —— 对所有球类与规则集完全一致,新增球类时零改动。

新增一个球类 = 新增一个 sports/xxx.ts 模块 + 若干模板。目录结构、注册表、模板渲染管线必须在 P0 就立起来,否则后期不是「扩展」而是「重构」。

P0 验收线

拔掉大屏网线 60 秒,大屏时间连续不跳变;恢复网络 1 秒内两端对齐且比分不丢不重;杀掉服务器进程,大屏时间依然准确,容器重启后比赛从 SQLite 完整恢复。

会踩的坑

以下每一条都会在赛场上真实发生,而不是在开发时。

Service Worker 与 Wake Lock 需要 HTTPS

局域网 http://192.168.x.x 下 PWA 与防锁屏全部失效。对策:启动时自签证书(含 LAN IP SAN)默认开 HTTPS,HTTP 降级,防锁屏用静音音频循环兜底。

校园网 AP 隔离

手机访问不到同网段服务器,全场开不了赛。对策:自带路由器/热点;「显示机本地跑服务端」模式;部署文档写清排查步骤。

中文队名 + 七段数码字体

七段字体没有中文字形,队名会掉字体或乱码,大屏直接毁掉。对策:数字与文字分字体栈,或内置 CJK 子集字体。

大屏电脑休眠与屏保

合盖后时钟冻结、比分停更。对策:页面 visibilitychange 时立即重取锚点;部署时关闭屏保与合盖休眠。

两台手机同时操作

并发操作导致比分错乱。对策:服务端串行化 + 乐观锁(seq),冲突命令拒绝并提示「另一台设备已操作」。

校赛规则五花八门

规则集写死,现场改不动。对策:规则集数据驱动,每场比赛可覆盖默认值(节数、节长、钟长、犯满、暂停次数)。

需要你拍板的九件事

这些答案会直接改变实现方案,尤其是第 3、5 两项。

  1. 大屏硬件是什么?投影仪还是 LED 屏?分辨率多少?需要几块?(决定模板字号、安全区与是否多屏同步)
  2. 同时几块场地开赛?每场地几个计分员?(决定是否需要多场地管理台,以及多设备并发防护的强度)
  3. 校赛规则细节?几节?每节几分钟?有没有 24 秒进攻钟?犯满罚出是 5 还是 7?每队几次暂停?(直接决定默认规则集,写错现场没法用)
  4. 要不要球员名单和每人得分/犯规?还是只要队伍总分?(FR-5 的实现量不小,影响排期)
  5. 部署机器是什么?有没有常开的电脑 / NAS / 小主机?接校园网还是独立热点?(决定自签证书方案与 IP 规划;没有常开机器就只能让笔记本一直开着)
  6. 手机构成?iPhone 多还是安卓多?要不要「添加到主屏幕」?(决定防锁屏与 PWA 的实现优先级,iOS 对 HTTPS 更敏感)
  7. 要不要直播推流?OBS 在哪台机器上?带宽多少?(决定 P1 是否做完整场景导演)
  8. 要不要赛后技术统计?需要 Excel 还是打印给教练?(决定事件日志要记到什么粒度,是否要记篮板等)
  9. 要不要校外远程看分?(若需要,就要引入公网暴露 + 鉴权,安全模型和部署方案都要改)
